# Порівняння naive RAG та sentence-window retrieval

## Executive Summary
Naive RAG зазвичай означає базовий підхід: документ розбивають на фіксовані чанки, кожен чанк ембедять і шукають найближчі за схожістю фрагменти без додаткового контекстного збагачення. Sentence-window retrieval — це вдосконалений варіант, де індексують окремі речення, але під час retrieval до знайденого речення підставляють його сусідні речення як контекст для генерації відповіді. Практично це часто краще працює для питань, де зміст розподілений між кількома реченнями або де важливі займенники, зв’язки між сутностями й локальний контекст.

## Findings

### 1) Що таке naive RAG
Базовий RAG-пайплайн зазвичай має такі етапи:
- розбиття документа на чанки;
- побудова ембедингів для чанків;
- пошук найбільш схожих чанків на запит;
- передача знайдених фрагментів у LLM для відповіді.

У статті про sentence-window retrieval прямо описано, що “naive chunking” часто використовує фіксований розмір чанка, наприклад за кількістю символів, і це може розрізати важливу інформацію між двома чанками. Для вирішення цього іноді використовують overlap, але тоді зростає дублювання і шум.

### 2) Що таке sentence-window retrieval
LlamaIndex описує sentence-window retriever як підхід, де:
- будують індекс по окремих sentence-level nodes;
- після retrieval вставляють текст вікна навколо знайденого речення перед synthesis.

Іншими словами, retrieval відбувається на дрібнішій одиниці — реченні, але модель отримує ширший локальний контекст навколо цього речення.

### 3) Основна різниця в механіці
**Naive RAG:**
- індексує chunks, які можуть містити кілька речень або навіть уривки речень;
- якість сильно залежить від того, як саме документ нарізано;
- якщо важливий факт або зв’язок розірвано на межі чанків, retrieval може не знайти повну відповідь.

**Sentence-window retrieval:**
- індексує окремі речення;
- після знаходження релевантного речення додає сусідні речення як контекст;
- краще зберігає локальну семантику і допомагає розв’язувати анафори/займенники.

### 4) Переваги sentence-window retrieval над naive RAG
Зі знайдених джерел випливають такі переваги:
- **менше ризику “розрізати” факт між чанками**;
- **краще відновлення контексту**, особливо коли важливе речення саме по собі коротке;
- **краще для займенників і локальних зв’язків** (“це”, “він”, “вона”, “воно”, прив’язка до сутності);
- **менше семантичного розмивання**, ніж у великих чанках.

Стаття Glaforge підкреслює саме цю ідею: векторне подання рахується по реченню, а ширший контекст додається лише на етапі відповіді.

### 5) Недоліки sentence-window retrieval
Цей підхід не є безкоштовним покращенням:
- **більше складності в пайплайні** — треба зберігати метадані про сусідні речення;
- **може збільшувати кількість токенів у prompt** через доданий контекст;
- **працює не завжди краще**, якщо питання потребує глобального огляду великого фрагмента, а не локального контексту;
- **частіше має сенс для текстів із виразною реченевою структурою** (статті, інструкції, юридичні тексти, технічна документація), ніж для дуже коротких або сильно табличних даних.

## Comparison / Analysis

| Критерій | Naive RAG | Sentence-window retrieval |
|---|---|---|
| Одиниця індексації | Фіксований chunk | Окреме речення |
| Контекст при генерації | Тільки знайдений chunk | Речення + сусідні речення |
| Ризик втрати важливого факту | Вищий, якщо факт на межі chunk | Нижчий, бо контекст додається після retrieval |
| Семантична точність retrieval | Середня, залежить від chunking | Часто краща для локальної семантики |
| Обсяг prompt | Часто менший або стабільний | Може бути більшим через window context |
| Складність реалізації | Нижча | Вища |
| Найкращі кейси | Простий baseline, швидкий старт | Тексти з локальними залежностями, займенниками, щільним контекстом |

### Практичний висновок
- Якщо потрібен **простий і дешевий baseline**, naive RAG підходить як стартова точка.
- Якщо якість відповіді страждає через **неповний контекст, розрив речень, займенники або дрібні факти**, sentence-window retrieval часто є кращим наступним кроком.
- Для багатьох реальних документів sentence-window retrieval — це не заміна всьому RAG, а покращення саме етапу chunking/retrieval.

## Key Trade-offs / Risks
- **Naive RAG** простіший, але сильніше залежить від якості chunking.
- **Sentence-window retrieval** часто точніший локально, але може підвищити latency і token cost.
- Жоден з підходів не гарантує кращий результат у всіх задачах: для деяких доменів краще працюють semantic chunking, hybrid retrieval або reranking.
- Оцінювати треба на власному наборі запитів, бо ефект сильно залежить від типу документів.

## Conclusion
Якщо коротко: **naive RAG** — це базовий підхід із фіксованими chunks, а **sentence-window retrieval** — більш точний варіант, де індексація йде по реченнях, а до знайденого фрагмента додається сусідній контекст. У більшості задач із текстами природної мови sentence-window retrieval має кращі шанси дати точнішу відповідь, але за ціну більшої складності та потенційно вищого споживання токенів.
