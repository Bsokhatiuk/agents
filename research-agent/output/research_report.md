# Порівняння підходів до побудови RAG: naive vs sentence‑window vs parent‑child retrieval

## Executive Summary
Три підходи відрізняються насамперед **гранулярністю індексації** (які шматки тексту векторизуються) та **тим, скільки контексту повертається в LLM**.

- **Naive RAG**: індексуємо фіксовані/семантичні чанки й повертаємо їх напряму в промпт. Найпростіший у реалізації, але часто програє в точності через компроміс “малий чанк = мало контексту / великий чанк = шум”.
- **Sentence‑window**: індексуємо *дуже дрібні* одиниці (речення), але **після** retrieval розширюємо їх “вікном” сусідніх речень і вже це подаємо в LLM. Дає кращу адресність пошуку при контрольованому контексті.
- **Parent‑child retrieval**: індексуємо *child* (дрібні) для точного матчу, але повертаємо *parent* (більші фрагменти/секції/документи) для достатнього контексту. Сильний підхід для довгих документів і питань, що потребують ширшого контексту, але дорожчий/складніший в інфраструктурі.

## Findings

### 1) Naive RAG (baseline)
**Ідея:**
1) розбити документи на чанки (часто фіксованого розміру з overlap);
2) закодувати ембеддингами; 
3) дістати top‑k найближчих чанків; 
4) вставити їх у промпт і згенерувати відповідь.

**Типові властивості/наслідки:**
- Вибір розміру чанку критичний: великі чанки дають більше контексту, але “розмивають” сигнал релевантності; малі — точніше матчаться, але можуть не містити потрібних пояснень/визначень/передумов.
- Часто потрібні додаткові техніки (reranking, hybrid search, query rewriting), щоб стабілізувати якість.

**Коли добре працює:**
- короткі, добре структуровані документи;
- FAQ‑контент, де відповідь локальна і вміщується в один чанк.

### 2) Sentence‑window retrieval
**Ідея:** індексація на рівні речень (дуже дрібні “child”), але повернення для LLM не одного речення, а **вікна** навколо нього (N речень ліворуч/праворуч).

**Ключовий механізм:**
- Retrieval працює по дрібній одиниці (речення), що підвищує шанс точного збігу.
- На етапі post‑processing retrieved sentence підміняється/розширюється на “window” сусідніх речень, щоб LLM отримала зв’язний контекст.

**Практичні плюси:**
- Зменшує типову проблему naive RAG: або шумний великий чанк, або “голе” речення без контексту.
- Добре для пошуку фактів/визначень/конкретних тверджень, які “живуть” в одному реченні, але потребують 1–3 речення пояснення.

**Мінуси/обмеження:**
- Працює найкраще в наративному тексті; у таблицях/коді/списках речення як одиниця може бути невдалою.
- Все одно може не дати “структурного” контексту (наприклад, цілий розділ з передумовами), якщо питання ширше.

### 3) Parent‑child retrieval (інколи: multi‑granularity / hierarchical retrieval)
**Ідея:** зберігати два рівні гранулярності:
- **Child chunks**: дрібні фрагменти (абзаци/речення/невеликі блоки), які індексуються у векторному сховищі.
- **Parent documents/chunks**: більші фрагменти (секція/сторінка/підрозділ/цілий документ), які не обов’язково повноцінно векторизуються для пошуку, але **повертаються** після знаходження релевантних child.

**Як це виглядає в retrieval:**
1) шукаємо top‑k child;
2) мапимо знайдені child до їх parent;
3) повертаємо parent (або top‑p parent) у контекст LLM.

**Плюси:**
- Поєднує точність дрібного матчу з достатнім контекстом “вгору по дереву”.
- Менше ризику “вирвати цитату з контексту” порівняно з поверненням лише дрібних фрагментів.
- Часто краще для довгих технічних документів, де відповідь розмазана по кількох абзацах одного розділу.

**Мінуси/ціна:**
- Складніша інфраструктура: потрібно зберігати зв’язки child→parent, окремий docstore/byte store, дедуплікацію parent, контроль довжини parent.
- Може збільшити токен‑витрати (parent довший за child/window) і латентність.

## Comparison / Analysis

### Порівняльна таблиця
| Критерій | Naive RAG | Sentence‑window | Parent‑child retrieval |
|---|---|---|---|
| Гранулярність індексації | середня (чанки) | дуже дрібна (речення) | дрібна (child) + ієрархія |
| Що передається в LLM | ті ж самі retrieved чанки | window навколо речення | parent фрагменти/секції |
| Точність retrieval (зазвичай) | середня | висока для локальних фактів | висока для локальних матчів + кращий контекст |
| Ризик “шуму” в контексті | середній/високий при великих чанках | нижчий (контрольований window) | середній (parent може бути довгим) |
| Ризик браку контексту | середній при малих чанках | нижчий, але залежить від window | низький (повертається більший контекст) |
| Складність реалізації | низька | середня | висока |
| Вартість/латентність | низька/середня | середня | середня/висока |
| Найкращі кейси | прості FAQ, короткі доки | точні відповіді з локального контексту | довгі доки, “розділові” питання |

### Як обрати (практичні евристики)
- Якщо ви тільки починаєте або потрібен швидкий baseline → **naive**.
- Якщо основний біль — “retrieval знаходить правильне місце, але LLM не вистачає сусіднього контексту” → **sentence‑window**.
- Якщо основний біль — “питання потребує ширшого контексту з розділу/сторінки, але retrieval має бути точним” → **parent‑child**.

## Key Trade-offs / Risks
- **Токени vs якість**: parent‑child часто дає кращий контекст, але може суттєво збільшити токен‑бюджет.
- **Дедуплікація**: у parent‑child декілька child можуть вести до одного parent; потрібна агрегація, щоб не дублювати контекст.
- **Границі “parent”**: якщо parent занадто великий, ви повертаєте шум; якщо занадто малий — втрачаєте сенс і перевагу підходу.
- **Тип контенту**: sentence‑window прив’язаний до коректного sentence splitting; для коду/логів/таблиць краще інші парсери/стратегії.

## Conclusion
- **Naive RAG** — простий і часто достатній, але чутливий до chunking.
- **Sentence‑window** — хороше “точкове” покращення для текстів, де сенс локалізований на рівні речень і потрібен невеликий контекст довкола.
- **Parent‑child retrieval** — більш універсальний і сильний для великих документів та складних питань, але вимагає складнішого зберігання, агрегації та контролю довжини контексту.
