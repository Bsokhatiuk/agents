# Порівняння підходів до побудови RAG: naive vs sentence-window vs parent-child retrieval

## Executive Summary
У RAG головна напруга — між **точністю пошуку** (краще працює на дрібних фрагментах) і **достатнім контекстом для генерації** (краще працює на більших фрагментах). 

- **Naive RAG**: один рівень чанків; що знайшли — те й віддали в LLM. Просто, дешево в розробці, але часто програє на питаннях, де відповідь вимагає локального контексту навколо знайденої фрази або коли великий чанк «розмиває» embedding.
- **Sentence-window retrieval**: індексуємо дрібно (речення/фрази), але на етапі відповіді **розширюємо** знайдене місце «вікном» сусідніх речень. Зазвичай дає кращу groundedness/релевантність при помірних змінах пайплайна.
- **Parent-child retrieval**: індексуємо **child**-чанки (дрібні) для пошуку, але повертаємо **parent**-чанки (більші) для генерації. Це більш загальний «small-to-big» патерн; добре працює для документів із багатьма темами в одному фрагменті та для довших, структурованих матеріалів.

## Findings

### 1) Naive RAG (baseline)
**Ідея**: розбити документи на чанки фіксованого розміру (часто з overlap), зробити embeddings, знайти top-k, і передати **ці ж чанки** в LLM.

**Типовий пайплайн**:
1. Chunking (наприклад 300–1000 токенів, overlap 10–20%)
2. Embedding кожного чанка
3. Vector similarity search (top-k)
4. (Опційно) rerank
5. Prompt = query + retrieved chunks

**Сильні сторони**:
- Найпростіший у реалізації та дебазі.
- Мінімальні вимоги до індексації/метаданих.
- Часто достатній для коротких, однорідних документів.

**Слабкі сторони**:
- **Компроміс “chunk size dilemma”**: малі чанки → краща точність пошуку, але бракує контексту; великі чанки → контекст є, але embedding «зашумлений» кількома темами.
- Може погіршувати groundedness через фрагментарність або через надлишок нерелевантного контексту у великих чанках.

---

### 2) Sentence-window retrieval
**Ідея**: будувати індекс на **дрібних одиницях** (часто реченнях), але після retrieval **підміняти/розширювати** текст для LLM, додаючи сусідні речення навколо знайденого речення (вікно).

**Як це описує LlamaIndex**: пак робить таке: *“Build input nodes … build a vector index over the input nodes, then after retrieval insert the text into the output nodes before synthesis.”* — тобто індексуємо одне, а в контекст для синтезу підставляємо вже «розширений» текст.  
Джерело: LlamaIndex docs — Sentence Window Retriever pack. 

**Що дає**:
- Висока точність пошуку (бо embedding на реченні/дрібному фрагменті).
- Достатній локальний контекст (сусідні речення) для правильної інтерпретації.

**Коли корисно**:
- Питання, де відповідь — одна/дві ключові фрази, але потрібні визначення/умови з сусідніх речень.
- Тексти, де логіка йде послідовно (статті, мануали, есе), і «локальне сусідство» є хорошою евристикою.

**Обмеження/ризики**:
- Вікно зазвичай **локальне**: якщо потрібний контекст у іншому розділі — не допоможе.
- Потрібно контролювати розмір вікна, інакше можна знову «роздути» контекст.

**Емпіричний сигнал** (як приклад сторонньої реалізації): у ноутбуці Грейсона Аткінса показано покращення метрик Answer Relevance і Groundedness порівняно з naive RAG на його експерименті. Це третинне джерело і результати залежать від датасету/налаштувань, але напрямок ефекту узгоджується з мотивацією методу.

Джерело: Grayson Adkins notebook (2024-04-10).

### 3) Parent-child retrieval (Parent Document Retrieval / small-to-big)
**Ідея**: розділити документи на **parent**-чанки (більші, “для читання LLM”) і додатково на **child**-чанки (дрібні, “для embeddings/пошуку”). Пошук відбувається по child embeddings, але повертаються parent тексти.

**Опис патерну (GraphRAG reference)**:
- вузький текст → «чистіший» embedding, кращий similarity search;
- але LLM може бракувати контексту;
- тому виконуємо vector search на child chunks, а потім дістаємо **parent** знайдених child chunks; опційно агрегуємо результати для одного parent.

Джерело: GraphRAG “Parent-Child Retriever” reference.

**Переваги**:
- Розв’язує “chunk size dilemma” більш системно: 
  - **child** оптимізовані під retrieval (precision), 
  - **parent** оптимізовані під synthesis (context/coherence).
- Зазвичай краще для довгих документів, де одна тема/факт потребує абзацного або секційного контексту.

**Недоліки/вартість**:
- Складніша індексація: потрібно зберігати зв’язки child→parent, додаткове сховище/метадані.
- Потенційно більше токенів у контексті (бо повертаємо більші parent-и), потрібні ліміти/дедуплікація/агрегація.

## Comparison / Analysis

| Критерій | Naive RAG | Sentence-window | Parent-child retrieval |
|---|---|---|---|
| Що індексуємо | середні/великі чанки | дрібні (часто речення) | child (дрібні) |
| Що віддаємо в LLM | ті самі чанки (як retrieved) | вікно речень навколо матчів | parent (більші фрагменти) |
| Точність retrieval | середня (залежить від chunk size) | висока на локальних фактах | висока (через дрібні child embeddings) |
| Контекст для відповіді | часто або замало, або забагато | достатній локально | часто найкращий баланс (coherent parent) |
| Складність реалізації | низька | середня | середньо-висока |
| Типові фейли | “не той чанк”, шум від великих чанків, втрата контексту при малих | потрібен нелокальний контекст; завелике/замале вікно | занадто великі parent-и → токени/шум; складність зберігання зв’язків |
| Найкраще підходить для | швидкий baseline, прості FAQ | статті/есе/мануали з локальною зв’язністю | довгі структуровані доки, багатотемні секції, коли потрібна цілісність |

## Key Trade-offs / Risks
- **Latency & cost**: parent-child часто збільшує середній розмір контексту (токени), sentence-window — керований ріст за рахунок фіксованого вікна.
- **Prompt stuffing**: і sentence-window, і parent-child можуть «роздувати» контекст; потрібні: top-k tuning, dedup, максимальна довжина контексту, reranking.
- **Дані з поганою структурою**: якщо документ погано сегментується (наприклад, таблиці/код/переліки), sentence-window може додавати «не той» контекст; parent-child залежить від якості parent-розбиття.

## Conclusion
- Починайте з **naive RAG** як контрольної точки (швидко дає робочий baseline).
- Якщо запити часто чіпляються за окремі фрази й їм бракує сусіднього пояснення — переходьте на **sentence-window** (мінімальна «надбудова» над baseline).
- Якщо ваші документи довгі, секційні, або embedding великих чанків погано працює через багатотемність, і при цьому LLM потрібні цілісні абзаци/розділи — **parent-child retrieval** зазвичай дає кращий баланс точність↔контекст, але ціною складності та токенів.
